# Spike: Better Auth against the hand-written authentication (FOR-148)

Date: 4 November 2026. Initiative "Platform architecture", project "Authentication foundation".
Better Auth version evaluated: 1.7.16 (npm, 4 November 2026), with `@better-auth/oauth-provider`,
`@better-auth/sso` and `@better-auth/api-key` at the same version.

## Question

Should Forgeron's authentication keep being written by hand, or move, fully or partly, to Better Auth?
Better Auth was never evaluated here (no mention in `docs/DECISIONS.md`).

## Verdict

1. **Keep the hand-written authentication.** Better Auth covers most of the surface, but not the parts
   that make ours fit: a session and a code bound to the workspace and to the asking browser (D-019,
   D-049), a verifier with a structural wrapping defence we have tests for (D-050), domain admission
   and the audit lines in the same batch (D-027, D-049).
2. **The one idea worth taking is not a library**: the Better Auth OAuth provider stores each protected
   resource as a database row, which answers FOR-19 and the D-013 cache cost. A later look at
   `@better-auth/oauth-provider` alone (not the whole framework) for FOR-107 is the only partial
   adoption worth a second spike; the current D-013 solution already works.
3. **Do not adopt Better Auth fully**: it adds a static `node:crypto` import and needs `nodejs_compat`,
   multiplies the bundle by 4 to 5, and moves identity tables and cookies we would then have to
   re-bind to a workspace ourselves.

## Method and limits

- Read what we have: `apps/gateway/src/identity/*`, `packages/registry` (migrations), D-013, D-015,
  D-019, D-027, D-031, D-035, D-036, D-041, D-046, D-049, D-050, D-051, D-053 (`docs/DECISIONS.md`).
- Read the Better Auth documentation on 4 November 2026 (pages listed under Sources). The pages were
  read through a summarising fetch, so option names were checked against the installed package types
  and source where it mattered.
- Prototype: a Worker with Hono and D1 (a 40-line Kysely dialect over D1), one Better Auth instance
  built per request, two workspaces on `acme.localhost` and `globex.localhost`, run in workerd through
  Miniflare 4.20260730.0 (compatibility date 2026-08-01, the newest that binary supports). Plugins:
  email OTP, magic link, organization, jwt, bearer, oauth-provider, api-key.
- The session was interrupted by a machine crash during the last test run, and the owner asked for the
  report without more builds or tests. **Every row below says whether it was run.** Anything marked
  "not run" is a documentation or source reading, not a result.
- Nothing was run against a real Cloudflare account, no real mail, no real identity provider.

Prototype code: not pushed (a push runs the full repository check, and builds were paused). It is a
copy of `spikes/better-auth` (sources, tests, `schema.sql`, pinned `package.json`) kept in the shared
notes folder of this session group, `better-auth-prototype/`, and in the spike worktree
`.claude/worktrees/spike-better-auth-7ee0bc` on the local branch `spike/better-auth-prototype`
(uncommitted). If the decision is to go on, push it before the worktree is cleaned.

## What Better Auth would replace, and what we would keep

Replace (if adopted): the code and magic-link flows, the session store, the OAuth server of FOR-107,
API keys, the organization model (members, invitations, roles).

Keep either way: the pages shell (D-053), the mail modes and the `MailSender` (D-049, D-051), the
rate limits per address, the audit lines in the same D1 batch as the change, per-person secrets
(D-036), the consent store (D-046), the `x-forgeron-user` header and the role access matrix
(`role_access`), deployment tokens, the revocation list. That is most of the identity code. The part
that disappears is mostly the flows we already wrote and tested.

## Migration shape if go

1. Add a migration creating the Better Auth tables with a prefix; never touch 0001 to 0019.
2. Copy `members` into `user`, `member` and an `organization` per workspace, keeping the member id so
   the audit lines and `group_members` still point at the same person.
3. Invitations and `membership_settings` copied to `invitation` and our own domain table (there is no
   domain auto-join to map to).
4. Sessions and `fgt` tokens: existing sessions end (8 h); personal tokens live up to 30 days and
   would need to stay valid through a dual verification period, because the signing key and the
   `jti` list (D-035) are ours.
5. A per-workspace check on every request, and a bound `aud`, written by us.
6. The SAML verifier would still be needed unless `samlify` is shown to run, and to pass the D-050
   cases, on Workers.

## Risks

- A stolen or misrouted session works on another workspace unless we add a check (shown).
- A scanner can sign someone in through a magic link (shown); the email code is not tied to the
  browser (shown).
- SAML: we would trust a library that the documentation does not say defends against signature
  wrapping, whose dependencies reference Node built-ins, and whose `allowIdpInitiated` defaults to
  `true` in the option table. Not run.
- The bundle grows by roughly 1.6 to 2 MB before the gateway's own code; startup cost in a Worker was
  not measured.
- Multi-resource tokens: one token can cover several tools (shown), against `sdk.md` section 7. A
  hook that rejects a second tool resource would be needed; not tried.
- Version churn: one framework controls the sessions, tokens and schema of every workspace, and the
  2.x line, plugin moves (`mcp()` and `oauthProvider()` exclusive) and a `nodejs_compat`
  requirement are outside our control.

## What this spike did NOT verify

- SAML through the SSO plugin in workerd, and the D-050 signature-wrapping and replay cases against
  it (the most important gap; the dependencies were read, not run).
- OIDC through Better Auth, invitations, roles, domain handling, API keys (read, not run).
- That a token for one tool is refused on another when verified with the JWKS (the test was in the
  run the crash interrupted), and the root `/.well-known/oauth-authorization-server` route.
- `__Host-` cookie naming, `Secure` behaviour over HTTPS, the cost of building one instance per
  request, parallel guessing of the code, and timing differences.
- A real D1 (Miniflare's D1 only), a real mailbox, a real MCP client, a real IdP.
- The Miniflare compatibility date was 2026-08-01, older than the gateway's 2026-10-01.

## Recommendation

Keep the hand-written authentication. Revisit only two narrow questions, each its own spike with
the test already written here: (a) `@better-auth/oauth-provider` as the authorization server for
FOR-107, with a hook that allows one tool per token, compared with extending D-013; (b) whether
`samlify` runs in workerd and passes the D-050 cases, which would let us delete our verifier, though
D-050 argued that the narrow verifier is the safer choice. Neither is needed now.
